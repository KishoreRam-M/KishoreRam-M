## 🧭 About Me

I'm a final-year Computer Science undergraduate at **Vel Tech Rangarajan Dr. Sakunthala Engineering College**, Chennai (Class of 2027), building toward one specific outcome: shipping systems where **AI agents and data pipelines are the same discipline**, not two separate resume bullets.

Most people treat "agentic AI" and "data engineering" as different tracks. I don't. Every agent I've built — a multi-agent admissions assistant, a natural-language-to-SQL studio, a healthcare RAG chatbot — is only as good as the data pipeline feeding it. So I build both ends: the **Spark/Kafka/Airflow pipeline that makes data trustworthy**, and the **CrewAI/LangChain agent layer that makes it usable**, wired together through **Java Spring Boot** services that don't fall over in production.

**What I'm optimizing for right now:**
- 🎯 Fresher/intern roles in **Agentic AI Engineering**, **Data Engineering**, and **Java backend development** — GCC and BFSI companies in the Chennai corridor
- 🏗️ A Data Engineering skill track built on **GCP**, with **PySpark** and **DP-203** as near-term milestones
- ✍️ Writing technical content on **Big Data, Hadoop, and HDFS internals** to force myself to actually understand the fundamentals, not just use the frameworks

**Engineering philosophy, in short:** if it can't survive a bad input, a slow network, and a 2 AM page, it isn't done — it's a demo.

## ⚙️ Engineering Principles

<table width="100%">
<tr>
<td width="33%" valign="top">

**Reliability & Observability**
Pipelines fail silently far more often than loudly. I design for the failure you don't notice — schema drift, partial writes, retry storms — with logging and validation baked in from the first commit, not bolted on after an incident.

</td>
<td width="33%" valign="top">

**Scalability by Design**
Code that works on 10k rows and dies on 10M rows isn't a smaller version of the real solution — it's a different problem. I prototype small but architect for the volume the system will actually see.

</td>
<td width="33%" valign="top">

**Ownership & First Principles**
I'd rather understand *why* Spark shuffles data across a stage than memorize the tuning flag that hides it. Frameworks change; the underlying distributed-systems tradeoffs don't.

</td>
</tr>
</table>

## 🏗️ Architecture I Build

The pattern behind most of my projects — raw data in, an agent making grounded decisions out:

```mermaid
flowchart TB
    subgraph Ingestion["Ingestion"]
        A["Source Docs / APIs / Forms"] --> B["Bronze — Raw Landing Zone"]
    end

    subgraph Processing["Processing"]
        B --> C["Silver — Cleaned & Validated"]
        C --> D["Gold — Curated Tables"]
    end

    subgraph Agentic["Agentic Layer"]
        D --> E["Vector Store — Retrieval"]
        E --> F["Multi-Agent Orchestration — CrewAI"]
        F --> G["LLM Reasoning — Gemini"]
    end

    subgraph Serving["Serving"]
        G --> H["API Layer — Spring Boot"]
        H --> I["End User Interface"]
    end
```

This is deliberately the same shape whether the "end user" is a prospective student asking about admissions, a claims adjuster reviewing a policy, or a hospital front desk — the medallion pipeline underneath doesn't change; only the agents and the domain data do.
